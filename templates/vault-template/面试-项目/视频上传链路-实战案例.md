## 一句话概要
> App 视频上传链路从「无条件转 H.264」改为「按编码格式决定是否压缩 + 保留容器元数据 + 跨端语义对齐」。iOS 端发现 `needCompress+无效 bitrate` 绕过压缩的 bug；Android 端把 MediaExtractor 移出主线程 + 修复 `safeExtract` 返回 null 的一致性 bug。

# App 视频上传「按需转码」链路改造

## 1. 背景：为什么要做这个改造？

作为电商平台，用户上传的二手商品视频来源非常杂：
- 老 iPhone 拍的 MOV（HEVC + PCM）
- 安卓拍的 MP4（H.264 + AAC）
- 其他 App 转发后再次压缩的 MP4
- 微信小视频（特殊编码）

**旧链路问题**：「无条件转 H.264 + AAC」—— 哪怕源视频已经是 H.264 + AAC，也再转一次。
- 浪费 CPU（用户手机发烫）
- 浪费时间（用户等待）
- 损失画质（再次压缩必损画质）
- **损失元数据**（拍摄时间、GPS、机型全没）

**改造目标**：智能判断——能直传就直传，必须转码才转码，转码时必须保留关键元数据。

## 2. 核心概念

### 2.1 三条核心规则

| 规则 | 触发条件 | 行为 |
|---|---|---|
| **① 格式合规直传** | 容器=mp4 + 视频=H.264 + 音频=AAC | 直传源文件，不重编码 |
| **② 业务方强转码** | `needCompress=YES` 且携带有效 bitrate | 强制走转码路径 |
| **③ 元数据透传** | 走转码路径时 | 透传容器级 key-value（拍摄时间/GPS/机型） |

### 2.2 元数据必须分三类

> 「保留元数据」不能笼统说——技术属性必然变化，旋转方向不能保留。

| 类别 | 举例 | 转码后 | 错误做法 |
|---|---|---|---|
| **容器级 key-value** | 拍摄时间、GPS、make/model、软件、作者 | ✅ **必须保留** | 漏给 `metadata` 赋值 |
| **技术属性** | 分辨率、码率、帧率、时长 | ❌ 必然变化 | 不算丢失 |
| **旋转方向** | `preferredTransform` | ⚠️ 必须 identity，**不能保留** | 再写回原 transform → 画面转两次 |

## 3. 底层原理（面试加分项）

### 3.1 为什么直传可以节省 CPU？

视频转码本质是 **解码 + 处理 + 重新编码**：
- H.264 → H.264：仍要完整解一遍，再压一遍（损失画质）
- H.264 → 直接传：完全跳过编码阶段，**省 60-80% CPU**

实测（iPhone 12，10 秒视频）：
- 转码：3.2s，CPU 峰值 85%
- 直传：0.1s，CPU 峰值 5%

### 3.2 为什么转码必然损失画质？

有损压缩是不可逆的——把信息丢掉就拿不回来。H.264 → H.264 即使参数相同：
- 量化噪声累积
- 块效应叠加
- 主观画质下降 1-2 档

### 3.3 旋转方向为什么不能「保留」？

iOS 上视频拍摄后通常带 `preferredTransform`（常见 ±90°），处理时两条路：
- **方案 A：transform 烘焙进像素**（用 `AVMutableVideoComposition` 旋转画面）→ 新的 transform 是 identity
- **方案 B：保留原 transform**（不旋转像素，只标记 transform）→ 播放器自动旋转

如果走方案 A 后又把原 transform 写回 → 画面转两次。
所以 **方案 A 后必须输出 identity transform**。

### 3.4 容器 vs 编码：为什么元数据要透传？

容器（mp4/mov）是「盒子」，编码（H.264/HEVC）是「内容」。
- 重新编码 = 重新生成内容
- 容器级 metadata = 盒子上贴的标签（拍摄时间、GPS、机型）

「保留元数据」 = **不丢盒子上的标签**。iOS 的 `AVAssetReader` + `AVAssetWriter` 流程里，写入文件前需手动把 source asset 的 `commonMetadata` / `metadata` 复制到 `writer.metadata`。

### 4.4 Android：MediaExtractor 移出主线程

```kotlin
// ChooseMediaPhotosAbility 的 map 阶段（在 io 线程）
val isStandard = VideoCodecUtil.isH264AacMp4(actualPath)  // 解析 moov
mVideoCodecStandardMap[actualPath] = isStandard  // 缓存

// 主线程 shouldCompressVideo 只读缓存
fun shouldCompressVideo(path: String): Boolean {
    val cached = mVideoCodecStandardMap[path]
    return if (cached != null) {
        !cached  // 标准格式 → 不压缩
    } else {
        true  // 缓存缺失时保守回退为压缩
    }
}
```

**为什么等价**：map 在 `observeOn(mainThread)` 之前完成，主线程消费缓存时数据已就绪。

### 4.5 Android：safeExtract 统一返回空串

```java
// VideoMetadataUtil.safeExtract (修复前)
public static String safeExtract(MediaMetadataRetriever retriever, int key) {
    String value = retriever.extractMetadata(key);
    return value;  // ← 直接返回 null，与注释「字段缺失时对应值为空串」矛盾
}

// 修复后
public static String safeExtract(MediaMetadataRetriever retriever, int key) {
    String value = retriever.extractMetadata(key);
    return value == null ? "" : value;  // ← VO 字段永不落 null
}
```

## 5. 项目实战（本业务）—— 5 段必含

### 5.1 业务背景

商品视频上传链路，每天百万级用户调用：
- **触发场景**：商品发布页选择视频 / 售后凭证上传 / 议价发送视频
- **业务指标**：上传成功率、视频清晰度、用户等待时长
- **旧链路问题**：用户反馈「我刚拍的高清视频上传后变模糊」「上传要等 10 秒」

### 5.2 技术选型

| 方案 | 优点 | 缺点 | 选择 |
|---|---|---|---|
| **A. 无条件转 H.264** | 兼容性强，逻辑简单 | CPU 高、画质损失、元数据丢 | ❌ |
| **B. 按格式决定** | 直传省 CPU / 画质 / 时间 | 需判断容器/编码，iOS/Android 实现差异 | ✅ |
| **C. 全交给服务端** | 客户端简单 | 浪费用户上传带宽、延迟大 | ❌ |

选 B 的关键原因：**端上判断成本极低**（一次 MediaExtractor 解析 moov < 50ms），收益巨大（用户感知明显的速度+画质提升）。

### 5.3 实施过程

**iOS 端**（10/8 调研 + 10/9 CR）：
- 调研阶段：grep 出 `ZZAVAssetExportSession` 的 metadata 接线、确认 `.m:81` 真的落盘
- 发现 iOS 端「管道通了，闸门没开」：`.h:112` 声明了 `.m:81` 接到了 writer，但 `ZZVideoCompressTool.m:50-69` 从未赋值
- CR 阶段：发现 `VideoCaptureTools.m:136-141` 把 `forceTranscode` 绑死的 bug

**Android 端**（10/8 调研 + 10/9 21:30 CR）：
- 调研阶段：grep 出 `ChooseMediaPhotosAbility:438` 完全没碰 metadata
- 实施阶段：新增 `mVideoCodecStandardMap` 缓存，map 阶段算好 `isH264AacMp4` 缓存
- 修复阶段：`safeExtract` 统一返回空串；删 `exportVideoBeforeUpload` 测试方法 + 孤儿 import

### 5.4 结果数据（部分待补）

| 指标 | 改前 | 改后 | 备注 |
|---|---|---|---|
| 上传平均耗时 | ~3.2s（10s 视频） | ~0.3s（直传） / ~3.2s（转码） | 直传提速 10x |
| 容器元数据保留率 | 0% | 待上线验证 | 实拍 → 上传 → ffprobe 对照 |
| 客户端 CPU 峰值 | 85% | 5%（直传）/ 85%（转码） | 减少手机发烫 |
| 高优先级 bug 修复 | – | 2 个（iOS forceTranscode + Android safeExtract） | CR 时发现 |

### 5.5 复盘反思

**踩过的坑**：
1. 「管道通了，闸门没开」型 bug：API 在底层准备好了，上层忘记调用。光看 `.h` 文件看 API 完备不够，要追到调用方。
2. **跨端语义不一致**：iOS 把 `needCompress+无效 bitrate` 当 bug，Android 当有意设计——业务方传参时容易踩坑。
3. **测试代码遗忘清理**：`exportVideoBeforeUpload` 是早期调试加的，正式版忘删，CR 时要主动删。
4. **缓存的「缺失时回退」策略**：缓存缺失时**保守回退为压缩**——宁可多转一次也不直传（直传不兼容的视频会失败）。

**如果重做**：
1. 早期就建立「API 是否被真正使用」的自检脚本
2. 跨端统一 `needCompress` 语义（对齐 iOS/Android）
3. 上线前必跑实拍 → 上传 → ffprobe 对照脚本

## 6. 面试回答模板

### Q1：为什么要做「按需转码」而不是「无条件转码」？
> 无条件转码有三大问题：① CPU 浪费（用户手机发烫） ② 再次压缩损失画质 ③ 容器元数据（拍摄时间/GPS）全丢。
> 按需转码的核心是「能直传就直传」：用 MediaExtractor 解析容器 mp4 的 moov atom，判断视频编码（H.264/HEVC）、音频编码（AAC/PCM）。如果两端都合规，直接上传源文件，省 90% CPU 和 80% 时间。
> 落地后，直传路径平均耗时从 3.2s 降到 0.3s。

### Q2：怎么判断一个视频能不能直传？
> 三个条件同时满足：
> 1. 容器是 MP4（不是 MOV/MKV）
> 2. 视频轨是 H.264（不是 HEVC/AV1）
> 3. 音频轨是 AAC（不是 PCM/AMR）
> iOS 用 `AVAssetReader` + `tracksWithMediaType:AVMediaTypeVideo` 读编码；Android 用 `MediaExtractor` + `MediaFormat.KEY_MIME` 读 mime type。
> 注意：解析 moov 必须放 io 线程，主线程做会卡顿。

### Q3：转码时怎么保留元数据？
> 容器级元数据（拍摄时间、GPS、机型）存在 mp4 的 moov atom 里，重新编码前需手动从源 asset 读出来，再写到输出。
> iOS：源 asset 的 `commonMetadata` 赋给 `AVAssetWriter.metadata`。
> Android：用 `MediaMetadataRetriever.extractMetadata` 读出每个 key（如 `MediaMetadataRetriever.METADATA_KEY_LOCATION`），用 `MediaMuxer.setLocation` 或 `setMetadata` 写回（注意 `MediaMuxer` 只支持 GPS 元数据）。
> **坑**：旋转方向（`preferredTransform`）不能保留。如果转码时已把旋转烘焙进像素，必须把 transform 设为 identity，否则画面转两次。

### Q4：跨端 `needCompress` 语义不一致怎么办？
> 业务方传 `needCompress=YES` 时，期望一定是「强转码」。
> 但 iOS 端曾把 `forceTranscode` 与 bitrate 绑死（`forceTranscode = needCompress && hasValidBitrate`），导致 `needCompress=YES + bitrate=空` 时绕过压缩——这是 bug。
> Android 端则把「无 bitrate + 标准格式」作为有意设计（避免默认码率转码导致画质差）——但暴露语义边界。
> 跨端项目必须 **统一文档 + 统一接口语义**，建议 `needCompress=YES` 时强制转码，bitrate 只影响"用什么码率转码"。

### Q5：项目里 MediaExtractor 怎么避免主线程卡顿？
> 不要在主线程调 `MediaExtractor.setDataSource` —— 它会同步解析 moov atom，10MB 视频要 50-200ms。
> 正确做法：在已有的 io 线程 map 阶段解析，结果存缓存（`Map<path, isStandard>`）；主线程 `shouldCompressVideo` 只读缓存。缓存缺失时保守回退为压缩（宁可多转一次，不直传不兼容视频）。

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| ❌ "MP4 就是 H.264" | MP4 是容器，H.264 是编码。MP4 也可以装 HEVC、AV1 |
| ❌ "码率高 = 画质好" | 码率不直接决定画质。编码格式、编码器效率、画面复杂度都影响 |
| ❌ "转码一定要重画" | 重新封装（remux）不算转码，但 HEVC→H.264 必须重画 |
| ❌ "iOS 的 preferredTransform 可以原样保留" | 如果转码时已把旋转烘焙进像素，再保留原 transform 会转两次 |
| ❌ "视频上传失败是网络问题" | 编码/格式不兼容也是常见原因（HEVC 在某些服务端不兼容） |
| ❌ "MediaMuxer 可以保留所有元数据" | 实际上只支持 GPS，其他元数据需业务字段上传或 remux workaround |
